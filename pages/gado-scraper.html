Gado-Scraper

Pipeline ETL com Git como banco de dados

Python pandas.read_html GitHub Actions Git Automation

O Problema

Para que o Sistema de Gestão de Gado calculasse o valuation do rebanho com precisão, ele precisava de cotações atualizadas da arroba do boi gordo e da novilha todos os dias. Inserir esses valores manualmente tornaria o ERP dependente de uma rotina humana, quebrando a proposta de automação.

A fonte de referência do mercado é a Scot Consultoria, que publica cotações diárias das 33 principais praças pecuárias do Brasil. O problema: nenhuma API pública, tabelas sem formato padronizado, e cabeçalhos que mudam sem aviso. O objetivo foi automatizar completamente essa coleta com custo de infraestrutura zero.

A Decisão de Arquitetura: Git como Banco de Dados

Rodar um servidor VPS só para executar um script diário seria desperdício de infraestrutura e custo. A solução foi usar o GitHub Actions como runner gratuito e agendado, mas o detalhe mais interessante está na persistência dos dados.

Em vez de um banco de dados convencional, o próprio repositório Git serve como armazenamento histórico. A cada execução, o robô commita o JSON atualizado de volta no repositório. O resultado é um histórico versionado de cotações, consultável via Raw URL pelo SGG, onde cada commit representa um dia de mercado.

Como Funciona

O arquivo atualizacao_diaria.yml dispara o pipeline todos os dias às 09:00 UTC via cron. O scraper usa pandas.read_html ancorado na string "Funrural" para identificar a tabela alvo — essa âncora semântica torna o scraper resiliente a mudanças de cabeçalho. Retry automático com 3 tentativas e backoff de 5 segundos garante robustez contra falhas transitórias de rede. O JSON resultante é commitado automaticamente, ficando disponível via Raw URL para o ERP consumir em tempo real.

A decisão técnica mais importante do projeto está em duas linhas. Em vez de selecionar a tabela por índice de posição (frágil a qualquer mudança de layout), o scraper a localiza por conteúdo semântico:

# Localiza a tabela que contém "Funrural" — resiliente a mudanças de layout
# Se o site mover ou adicionar tabelas, o pivot semântico ainda funciona
tabelas = pd.read_html(StringIO(html), decimal=",", thousands=".", match="Funrural")

# Erro explícito se o layout mudar — falha rápida em vez de dados silenciosamente errados

Cada commit diário é um snapshot auditável das cotações daquele dia. O histórico completo pode ser reconstruído via build_dataset.py, que percorre o git log e reconstrói os CSVs acumulativos com deduplicação por (data, praça).

O que eu faria diferente

Git como banco de dados é elegante para esse volume, mas tem limites claros: consultas históricas exigem checkout de commits ou parsing do log, e não há suporte a queries relacionais. Se o escopo crescesse para múltiplas fontes de dados ou análises mais complexas, eu migraria a persistência para um banco de séries temporais como TimescaleDB, mantendo o GitHub Actions como runner. A âncora de scraping por string semântica em vez de posição de coluna foi a decisão mais valiosa do projeto — salvou retrabalho em pelo menos duas mudanças de layout do site-fonte.
